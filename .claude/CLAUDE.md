# TicTacToe — 终端井字棋（C23，双 UI 后端）

非代码的文档，会话，思维链全部用中文输出

C 语言（C23）写的终端井字棋。同一套游戏逻辑配两套界面后端：Cygwin/Unix 走 ncurses，原生 Windows 走 Win32 控制台 API（零第三方依赖，产出的单个 exe 可直接发给别人）。

---

## 构建

CMake（≥ 4.2），`CMakeLists.txt` 按平台自动选后端：

| 平台 | 条件 | 源文件 | 依赖 |
|---|---|---|---|
| Cygwin / Unix | `NOT (WIN32 AND NOT CYGWIN)` | `main.c` + `game.c` | ncurses（宽字符版） |
| 原生 Windows | `WIN32 AND NOT CYGWIN` | `win32_main.c` + `game.c` | 无，只用 KERNEL32/msvcrt |

```bash
cmake -S . -B build && cmake --build build
```

可执行文件直接产出到项目根目录（`CMAKE_RUNTIME_OUTPUT_DIRECTORY`）。

### 构建环境约束（本机实测）

- **唯一的 C 工具链是 Cygwin64 gcc**（GCC 14.4.0）。没有 MSVC、没有 clang；MinGW 是为做原生 exe 另装的。
- **Cygwin gcc 不定义 `_WIN32`**，只定义 `__CYGWIN__`，且环境里没有 `windows.h`。所以 Cygwin 侧只能走 POSIX/ncurses，PDCurses 和 termbox2 的 Windows 分支在这里都用不了。
- **`CURSES_NEED_WIDE TRUE` 不能删**：去掉就会链到窄字符版 libcurses，制表符和中文都画不出来。
- **项目目录名必须是纯 ASCII**。目录名里出现非 ASCII 字符（曾经是 U+2011 非断行连字符），MinGW 的 `ld.exe` 按系统 ANSI 代码页编码文件名会失败，导致在该目录（含子目录）下无法链接出任何 exe。

## 代码结构

```
game.h / game.c   游戏逻辑，与界面无关，两个后端共用
bot.h / bot.c     机器人选点，两个后端共用
store.h / store.c 存档与战绩的文件读写，两个后端共用
main.c            ncurses 后端（Cygwin / Unix）
win32_main.c      Win32 控制台后端（原生 Windows）
```

- **数据模型**：`Game` 里 `int cell[3][3]`（0 空位 / 1 白子 / 2 黑子）、`cur` 当前方、`cr,cc` 光标格、`winner`、`moves`。胜负判定靠 `game.c` 的 `WIN_LINES[8][3][2]`（3 行 + 3 列 + 2 对角），`game_place()` 负责判胜 / 判平 / 换手。
- **棋盘几何**：外框固定 13 列 × 7 行（每格 3 列宽，格线占 1 列/行）。两个后端共用同一套坐标公式 —— `cell_y(r) = by + 1 + 2r`、`cell_x(c) = bx + 2 + 4c`。
- **两个后端保持镜像结构**：`layout / draw_board / draw_cells(draw_dynamic) / draw_status(draw_help)` 一一对应，键值也沿用 curses 的编码习惯（`win32_main.c` 里自定义 `KEY_UP` 等宏）。改一个后端时对照另一个。
- **五个界面**：主菜单（人机对战 / 双人对战 / 继续 / 查看记录 / 退出）、难度选择、投色子、棋局、对局记录。两个后端各自维护一个 `scr` 状态变量，各页的绘制函数也各自一份（保持镜像）。
- **人机对战流程**：菜单 → 难度选择 → 投色子（双方各掷 1~6，大的执白先下，平手重掷，有滚动动画）→ 棋局。对局状态（谁是人、谁是机器人、难度）存在 `main.c` / `win32_main.c` 各自的 `g_mode / g_bot_side / g_level` 里，不进 `Game`，让 `game.c` 保持纯规则。
- **机器人**（`bot.c`）：`BOT_HARD` 是 minimax 搜到底、永不输；`BOT_EASY` 是「能赢就赢、但从不堵」。两个后端都在主循环**开头**检查 `bot_turn()` 让机器人落子（含机器人执白时开局那一步），落子前先重画一帧并停 400ms（ncurses 用 `napms`，Win32 用 `Sleep`），免得玩家看不清自己刚下的那手。
- 操作：菜单里方向键选择、回车确认；棋局里方向键移动、回车/空格落子、`r` 重开（机器人执子不变）、`q`/ESC 回主菜单。终端过小时显示"终端太小，请放大窗口"，阈值是 `COLS < BOARD_W+2 || LINES < BOARD_H+6`。
- **鼠标**：只做「点击即生效」，不做悬停高亮（运动事件量大、部分终端会卡）。做法是**把点击翻译成等价的按键**（`mouse_key()`），之后走和键盘完全相同的那套分发 —— 这样不用为鼠标再写一遍各页的逻辑，两个后端也天然保持镜像。命中判定靠 `item_at()`（菜单项占两行）和 `cell_at()`（棋盘格反查），后者的坐标公式必须和 `cell_x/cell_y` 对得上，所以菜单/难度页的原点抽成了 `menu_x/menu_y`、`level_x/level_y`，绘制和命中共用。
  - ncurses 侧：`mousemask(BUTTON1_CLICKED | BUTTON1_PRESSED, NULL)`，事件从 `getch()` 以 `KEY_MOUSE` 返回，`getmouse()` 取坐标。**两个位都要开**：只开 `CLICKED` 时，一旦 ncurses 把按下和松开读成两批，它会超时改报 `PRESSED`，而该位不在掩码里 —— 事件整个丢掉（实测偶发）。两个位都开时，按下+松开报一个 `CLICKED`、只有按下则报一个 `PRESSED`，都只触发一次。
  - **本机 terminfo 只声明了 SGR 协议（`kmous=\E[<`），X10 编码（`ESC[M`）解不出来**。写自动化测试注入点击时**必须按下+松开一起发**（真实终端就是这样）：只发按下的话 ncurses 认为按钮一直按着，第二次点击起 `getmouse()` 就返回失败。
  - **Cygwin 侧只有 mintty 里能用鼠标**：跑在 cmd.exe / Windows Terminal 里时 Cygwin 用 `cygwin` 这个 terminfo 条目，它**没有 `kmous` 能力**。所以提示行是否显示「鼠标可点」由 `mousemask()` 的返回值决定（`g_mouse_ok`），免得在没有鼠标的终端上误导用户。
  - Win32 侧：`ui_init()` 里加 `ENABLE_MOUSE_INPUT`，并且**必须清掉 `ENABLE_QUICK_EDIT_MODE`**（要同时带 `ENABLE_EXTENDED_FLAGS` 才改得动），否则点击会被控制台当成选中文本吃掉，事件根本传不到程序。`read_key()` 里认 `MOUSE_EVENT`，坐标是**缓冲区坐标**，要减 `g_ox/g_oy` 换成窗口坐标。
- **存档与战绩**：`store.c` 读写 exe 同目录的 `tictactoe.dat`（纯 ASCII「键 值」行格式，认不出的键跳过、缺键用默认值，所以文件坏了也不会崩，加新键也不会让旧文件失效）。双人和人机战绩分开记。每落一子写一次；一局终局时把结果计入战绩并清掉存档。没有存档时菜单里的「继续」变暗、回车无效。

## 编码陷阱

### 中文和制表符必须先设编码

- ncurses 版：`main()` 开头 `setlocale(LC_ALL, "")`，否则 `┌─┬─┐`、`●○` 和中文全是乱码。
- Win32 版：`SetConsoleOutputCP(CP_UTF8)`，且输出一律走 `WriteConsoleW`（不用 `printf` 直接写屏）。

### 别用 PDCurses 做原生 exe

PDCurses 的 wincon 端口把虚拟屏按"一个字符一格"存储，而 Windows 控制台里汉字占 2 格，`_new_packet()` 里 `WriteConsoleOutput` 的矩形宽度算少了 —— 症状是**每多一个汉字，行首就多丢一个字符**（制表符和 `●○` 是单宽，所以只有汉字触发）。

`win32_main.c` 因此改成 `SetConsoleCursorPosition` + `SetConsoleTextAttribute` + `WriteConsoleW` 逐行原地重绘：控制台自己会按字符的显示宽度前进，双宽由系统处理，不用手工算格子。

### ncurses 方向键是 SS3 形式

本机 terminfo 的 `xterm-256color` 里方向键发 `ESC O A/B/C/D`（SS3），不是常见的 `ESC [ A`（CSI）。原因是 `keypad(stdscr, TRUE)` 会发 `smkx` 把终端切到应用光标键模式（DECCKM）。`getch()` 能正确返回 `KEY_UP` 等，**不要手工解析转义序列**。

## 验证

- 游戏逻辑（`game.c`）纯计算、无 IO，可直接写单元测试。
- TUI 用伪终端自动化验证：`forkpty()` 起子进程 → 往主端写按键字节 → 收主端输出。要点：**必须把整段输出累积到缓冲区、最后一次性解析**，边读边解析会在块边界切断多字节字符和转义序列（症状是画面零星丢字）。要还原最终画面需要一个小型 ANSI 解释器，处理 `ESC[r;cH` 定位、`ESC[2J` 清屏、`ESC[K` 清行、`ESC[A/B/C/D` 相对移动即可。`forkpty` 的第 4 个参数 `struct winsize` 可模拟任意终端尺寸，用来测小终端保护。
- 注意：**不要用 `ungetch()` 注入转义序列来测方向键**，它会绕过 ncurses 的序列匹配状态机，结果永远不匹配。
- 坑：**ncurses 只发差分，屏幕没变的字符不会重发**。所以「这一步画面上应该有某某文字」这类断言经常不成立——比如上一屏是「回车投掷」、这一屏是「回车开始」，公共前缀「回车」就不会出现在输出里。判断状态变化要靠存档文件或别的可观测副作用，别指望在输出里搜到完整的整行文字。

# 行为准则（通用）

减少常见 LLM 编码错误的行为准则。可根据项目特定需求进行合并。

**权衡取舍：** 这些准则偏向于谨慎而非速度。对于琐碎任务，自行判断即可。

## 1. 先思考再编码

**不要臆测。不要隐藏困惑。主动暴露权衡。**

在实现之前：
- 明确陈述你的假设。如果不确定，就问。
- 如果存在多种解释，把它们都列出来——不要默默自行选择。
- 如果存在更简单的方案，直接说出来。必要时据理力争。
- 如果有不清楚的地方，停下来。指出哪里令人困惑。提问。

## 2. 简单优先

**以解决问题所需的最少代码为准。不写投机性代码。**

- 不添加超出需求的功能。
- 不为一次性代码做抽象。
- 不添加未经要求的"灵活性"或"可配置性"。
- 不为不可能出现的场景写错误处理。
- 如果写了 200 行而 50 行就能解决，重写它。

问问自己："资深工程师会觉得这过度复杂吗？"如果是，就简化。

## 3. 外科手术式修改

**只动必须动的。只清理自己造成的混乱。**

编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有问题的东西。
- 匹配现有风格，即使你会用不同的方式写。
- 如果发现无关的死代码，提出来——但不要删除它。

当你的修改产生孤儿代码时：
- 删除因你的改动而不再使用的导入/变量/函数。
- 未经要求，不要删除先前存在的死代码。

检验标准：每一行改动都应能直接追溯到用户的需求。

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：
- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复这个 bug" → "编写能复现它的测试，然后让它通过"
- "重构 X" → "确保重构前后测试都通过"

对于多步骤任务，陈述简要计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

明确成功标准可以让你独立循环推进。模糊的标准（"把它搞定"）则需要不断澄清。

---

**这些准则有效体现在：** diff 中不必要的改动更少，因过度复杂化而重写的次数更少，而且澄清问题出现在实现之前，而不是犯错之后。
